## 1. 設計方針

- 「記事URLを音声化し、バックグラウンドで最後まで聴く」という一つの体験を優先する。
- 初期構成は単一のExpoアプリ、単一のFastAPIサービス、単一の永続Volumeとする。
- 会員・クラウド同期・サーバーDB・ジョブキューをMVPでは持たない。
- 外部APIキーはサーバーだけで保持する。
- URL取得機能はSSRFの攻撃面になるため、入力形式だけでなく名前解決後とリダイレクト後も検証する。
- 将来、オブジェクトストレージ、DB、非同期ジョブへ置換できる境界を保つ。

## 4. コンポーネント設計

### 4.1 モバイルアプリ

| コンポーネント  | 責務                                                      |
| --------------- | --------------------------------------------------------- |
| URL入力フォーム | URL入力、クライアント側検証、生成開始                     |
| 生成状態ビュー  | 処理中、成功、失敗と再試行を表示                          |
| APIクライアント | FastAPIとの通信、タイムアウト、レスポンス変換             |
| ポーリング制御  | 2秒間隔で状態を取得し、完了・失敗・5分超過時に停止        |
| Audio Player    | MP3のロード、再生、一時停止、バックグラウンド再生         |
| セッション状態  | 現在の1記事だけをメモリで保持。履歴・再生位置は保存しない |

音声ライブラリは `expo-audio` を前提とする。Androidではバックグラウンド再生、オーディオ通知・メディア制御を、iOSではBackground Audio Modeと適切なオーディオセッションを有効化する。Android 10以降およびiOS 15以降の実機で検証する。MVPのプレイヤー操作は再生・一時停止だけとする。

### 4.2 FastAPI

| モジュール          | 責務                                                   |
| ------------------- | ------------------------------------------------------ |
| Router              | HTTP入力、応答コード、スキーマ変換                     |
| URL Validator       | スキーム、ポート、ホスト、解決IP、リダイレクト先の検証 |
| Article Fetcher     | タイムアウト・サイズ上限付きHTML取得                   |
| Article Extractor   | タイトルと主要本文の抽出                               |
| Text Normalizer     | 空白整理、不要要素除外、読み上げ用整形                 |
| Text Chunker        | TTS上限に合わせた段落単位の分割                        |
| TTS Adapter         | TTSベンダー固有APIの隠蔽、再試行、音声取得             |
| Audio Assembler     | 複数チャンク音声の連結または連続再生用整列             |
| Metadata Repository | JSONメタデータの読み書きと原子的更新                   |
| Audio Repository    | MP3保存、存在確認、安全なパス解決                      |

記事抽出はPythonの `trafilatura` を使用し、FastAPIプロセス内で完結させる。Mozilla Readability用のNode.jsサービスは追加しない。受入記事群で抽出精度が不足した場合だけ、サイト別調整または抽出ライブラリの再評価を行う。

| 項目       | 仕様                                                           |
| ---------- | -------------------------------------------------------------- |

| エラー     | 内部例外ではなく、ユーザーが理解できる分類済み文言             |

## 6. API設計

音声生成は数十秒以上かかる可能性があるため、開始と状態取得を分ける非同期方式を採用する。会話上の `POST /generate` と `GET /audio/{id}` を保ちつつ、状態確認APIを追加する。`POST /generate`、`GET /jobs/{id}`、`GET /audio/{id}` にはテスター共通の `X-MVP-Key` ヘッダーを要求する。`GET /health` はヘルスチェック用として認証対象外とする。

### 6.1 POST `/generate`

変換処理を開始する。

Request:

```json
{
  "url": "https://example.com/article"
}
```

Response `202 Accepted`:

```json
{
  "id": "01JEXAMPLE0000000000000000",
  "status": "queued",
  "status_url": "/jobs/01JEXAMPLE0000000000000000"
}
```

主なエラー:

| Status | コード                | 条件                   |
| ------ | --------------------- | ---------------------- |
| 400    | `INVALID_URL`         | 形式・スキームが不正   |
| 403    | `URL_NOT_ALLOWED`     | 内部IP等の取得禁止先   |
| 413    | `ARTICLE_TOO_LARGE`   | 取得量・本文量上限超過 |
| 429    | `RATE_LIMITED`        | 利用回数超過           |
| 503    | `SERVICE_UNAVAILABLE` | TTS等が一時利用不能    |

### 6.2 GET `/jobs/{id}`

変換状態を返す。

Response `200 OK`（処理中）:

```json
{
  "id": "01JEXAMPLE0000000000000000",
  "status": "generating_audio",
  "title": "記事タイトル",
  "created_at": "2026-08-05T11:00:00Z",
  "updated_at": "2026-08-05T11:00:08Z"
}
```

Response `200 OK`（完了）:

```json
{
  "id": "01JEXAMPLE0000000000000000",
  "status": "ready",
  "title": "記事タイトル",
  "source_url": "https://example.com/article",
  "audio_url": "/audio/01JEXAMPLE0000000000000000",
  "duration_seconds": 742,
  "created_at": "2026-08-05T11:00:00Z",
  "updated_at": "2026-08-05T11:00:24Z"
}
```

Response `200 OK`（失敗）:

```json
{
  "id": "01JEXAMPLE0000000000000000",
  "status": "failed",
  "error": {
    "code": "ARTICLE_EXTRACTION_FAILED",
    "message": "この記事から本文を取得できませんでした。別の記事でお試しください。"
  }
}
```

状態値:

```text
queued
fetching
extracting
generating_audio
ready
failed
```

### 6.3 GET `/audio/{id}`

生成済みMP3を返す。

- Content-Type: `audio/mpeg`
- Range Request: Android/iOSプレイヤーの安定したストリーミング再生のため対応する
- `404`: IDが存在しない、未完了、または削除済み
- ファイル名は外部入力ではなくサーバー生成IDから決定する

### 6.4 GET `/health`

サービス起動確認用。秘密情報や内部構成を返さない。

```json
{
  "status": "ok"
}
```

## 8. 非同期処理設計

MVPではFastAPIのプロセス内バックグラウンド処理を採用する。ただし、プロセス再起動で実行中ジョブが失われるため、次を満たす。

- 開始時に `queued` のメタデータを永続化する。
- 各段階で状態と更新日時を原子的に更新する。
- 起動時に長時間 `queued` / 処理中のジョブを `failed` として回収する。
- 1プロセス内の同時生成数を2件に制限する。
- 生成ジョブは開始から5分でタイムアウトさせる。
- 規模拡大時はRedis + RQ/Celery等へ置き換える。

ジョブキューが満杯の場合は `429 RATE_LIMITED` を返す。再起動で失敗扱いになったジョブは、ユーザーが明示的に再試行するまで再実行しない。

## 9. データ・ファイル設計

### 9.1 ディレクトリ

```text
/data/
├── audio/
│   └── {id}.mp3
├── metadata/
│   └── {id}.json
└── tmp/
    └── {id}/
        ├── chunk-0001.mp3
        └── chunk-0002.mp3
```

一時ファイルは成功・失敗の終了処理で削除する。パスに元URL、記事タイトル、ユーザー入力を使用しない。

### 9.2 メタデータ

```json
{
  "id": "01JEXAMPLE0000000000000000",
  "source_url": "https://example.com/article",
  "title": "記事タイトル",
  "status": "ready",
  "audio_path": "/data/audio/01JEXAMPLE0000000000000000.mp3",
  "duration_seconds": 742,
  "character_count": 8200,
  "created_at": "2026-08-05T11:00:00Z",
  "updated_at": "2026-08-05T11:00:24Z",
  "expires_at": "2026-08-06T11:00:00Z",
  "error_code": null
}
```

書き込みは一時ファイルへ保存後にrenameするなど、途中状態のJSONが読まれない方法を採用する。同じIDへの同時更新を排他する。作成から24時間後にMP3、メタデータ、一時ファイルを定期削除する。削除処理は起動時と1時間ごとに実行する。

### 9.3 ID

- 推測困難で衝突しにくいUUIDv4またはULIDをサーバーで生成する。
- 音声取得に認証を設けない場合、列挙されにくさだけを認可の代替にしない。少人数テスト用の保護方式を別途決める。

## 10. URL取得・セキュリティ設計

### 10.1 許可

- `https` を標準とし、必要な場合のみ公開先の `http` を許可する。
- 標準ポートのみを基本とする。

### 10.2 拒否

- `file:`, `ftp:`, `data:` 等の非HTTP(S)スキーム
- URL内のユーザー情報
- localhostおよびループバック
- RFC1918プライベートIP
- リンクローカル、マルチキャスト、予約済み、メタデータサービス等
- IPリテラルは拒否する

### 10.3 取得時の制御

- DNSの全解決結果を検査する。
- 接続直前の解決先固定または同等のDNS rebinding対策を行う。
- リダイレクトは自動追従せず、回数を制限し、遷移先を毎回再検証する。
- 接続・読み取り・全体タイムアウトを設定する。
- Content-TypeとContent-Lengthを確認し、ストリーミング読込中も上限を強制する。
- 圧縮展開後のサイズ上限も考慮する。

## 11. TTS設計

Google Cloud Text-to-Speechを使用し、TTS Adapterにベンダー固有処理を閉じ込める。

```text
synthesize(text, voice, format) -> AudioChunk
```

- 言語は `ja-JP`、音声は `ja-JP-Wavenet-A`、出力はMP3、読み上げ速度は1.0を初期値とする。
- 記事本文は3万文字を上限とし、段落境界を優先して1チャンクのUTF-8入力を4,500バイト以下に分割する。Google Cloud TTSの上限は1リクエスト5,000バイトで、日本語1文字は複数バイトになるため、文字数ではなくバイト数で判定する。
- 分割順を固定し、欠落・重複がないことを検査する。
- 429、5xx、通信タイムアウトのみ指数バックオフ付きで限定再試行する。
- 認証・入力不正等は再試行しない。
- 音声フォーマットはMVPではMP3に統一する。
- 音声、速度、言語、最大文字数、再試行回数を環境設定とする。
- 複数チャンクはFFmpegで順番どおりに単一MP3へ連結し、再生時間とファイルの読込可否を検査してから `ready` にする。
- 月間入力文字数をメタデータとは別の月次カウンターで管理する。TTS呼び出し前に使用予定文字数を原子的に確保し、500万文字を超えるジョブは呼び出し前に拒否する。
- 2026-08-05確認時点の料金はWaveNet音声が月400万文字まで無料、その後100万文字あたり4米ドルである。実装・運用時は[Google Cloud公式料金](https://cloud.google.com/text-to-speech/pricing?hl=ja)を再確認する。

## 12. エラー設計

| 内部分類                    | ユーザー表示例                                         | 再試行   |
| --------------------------- | ------------------------------------------------------ | -------- |
| `INVALID_URL`               | 正しい記事URLを入力してください                        | 修正後可 |
| `URL_NOT_ALLOWED`           | このURLは利用できません                                | 不可     |
| `ARTICLE_FETCH_FAILED`      | 記事を取得できませんでした                             | 可       |
| `ARTICLE_EXTRACTION_FAILED` | この記事から本文を取得できませんでした                 | 原則不可 |
| `ARTICLE_TOO_LARGE`         | この記事は長すぎるため変換できません                   | 不可     |
| `TTS_TEMPORARY_ERROR`       | 音声を生成できませんでした。時間をおいてお試しください | 可       |
| `AUDIO_NOT_FOUND`           | 音声が見つかりません。再生成してください               | 可       |
| `NETWORK_ERROR`             | 通信を確認して再試行してください                       | 可       |

レスポンスにはスタックトレースや外部サービスの生エラーを含めない。詳細はリクエストIDとともにサーバーログへ残す。

## 14. ログ・監視

- 構造化ログに `request_id`, `job_id`, `stage`, `result`, `duration_ms`, `error_code` を含める。
- URLは必要ならホスト名のみ、またはマスキングした値を記録する。
- 記事本文、TTSキー、認証情報を記録しない。
- 最低限、APIの5xx、ジョブ失敗率、TTS所要時間、Volume使用量、TTS利用量を確認する。
- `/health` をRailwayのヘルスチェックに利用する。

### 14.1 費用管理

- Google CloudとRailwayの請求アラートを設定し、EASを含む月額総見込み8,000円で警告する。
- アプリ側とは別にサーバー側で月間500万文字のハード上限を強制する。
- 月額総見込みが8,000円に達した場合は管理者が新規生成を停止し、1万円までの余裕を予期しない従量課金に残す。
- 無料枠、料金、為替は変動するため、毎月初回の運用確認で見直す。

## 15. テスト方針

### 15.1 単体テスト

- URL形式・禁止IP・リダイレクト検証
- 本文抽出の代表HTMLと失敗HTML
- テキスト分割の境界、長段落、空本文
- 状態遷移とJSON原子更新
- TTS Adapterの再試行可否
- ファイルパスの安全性

## 16. デプロイ設計

### 16.1 API

1. FastAPIコードをGitHubへpushする。
2. Railwayをリポジトリへ接続し、Dockerfile等からビルドする。
3. `/data` にVolumeをマウントする。
4. 環境変数とヘルスチェックを設定する。
5. 公開HTTPS URLを発行する。
6. 実記事を用いたスモークテストを行う。

### 16.2 モバイル

1. Preview環境の `EXPO_PUBLIC_API_URL` をEASに設定する。
2. Android/iOSのDevelopment Buildで固定MP3のバックグラウンド再生を検証し、Android Preview APKとiOSのTestFlight用配布ビルドを作成する。
3. バックグラウンド音声設定を含む実機ビルドで検証する。
4. AndroidはPreview APK、iOSはTestFlightで最大10人のテスターへ配布する。
